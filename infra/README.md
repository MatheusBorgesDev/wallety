# Infrastructure

The API and the webhook delivery process run as containers on Google Cloud Run, from the same image, with
PostgreSQL on Neon. Deployment is a job of the
CI workflow: it runs only for pushes to `main`, after every check passed.

## One-time setup

`gcp-setup.sh <PROJECT_ID>` prepares a Google Cloud project. It can be run again safely. It creates:

- an Artifact Registry repository for the images;
- a runtime service account for the API, one for the delivery process and a deploy service account for GitHub Actions;
- Workload Identity Federation restricted to the `main` branch of this repository, so no long-lived key exists;
- three empty secrets for the database connection strings, and the webhook signing secret and the access token secret, both of which it generates;
- the public Cloud Run service of the API and the private one of the delivery process, both with a placeholder image.

The values it prints are stored as GitHub Actions repository variables. None of them is a secret.

## Database roles

The migrations create three group roles that cannot log in:

| Role | May do |
|---|---|
| `wallety_app` | Read and insert. Update on sandboxes, users and accounts. No update or delete on transfers and ledger entries: the ledger is append-only for the API |
| `wallety_dispatch` | Read outbox events and update their delivery state. No access to the ledger |
| `wallety_purge` | Read and delete, for the cleanup job |

Each environment creates its own login roles as members of these. In production, run once as the database
owner, with a generated password:

```sql
DO $$
BEGIN
  IF NOT EXISTS (SELECT 1 FROM pg_roles WHERE rolname = 'wallety_app') THEN
    CREATE ROLE wallety_app NOLOGIN;
  END IF;
  IF NOT EXISTS (SELECT 1 FROM pg_roles WHERE rolname = 'wallety_dispatch') THEN
    CREATE ROLE wallety_dispatch NOLOGIN;
  END IF;
END;
$$;

CREATE ROLE wallety_api LOGIN PASSWORD '<generated password>' IN ROLE wallety_app;
CREATE ROLE wallety_dispatcher LOGIN PASSWORD '<another generated password>' IN ROLE wallety_dispatch;
```

## Secrets

All of them live in Secret Manager and nowhere else.

| Secret | Value | Read by |
|---|---|---|
| `wallety-database-url` | Connection string of the `wallety_api` login | The API, at runtime |
| `wallety-dispatch-database-url` | Connection string of the `wallety_dispatcher` login | The delivery process |
| `wallety-migration-database-url` | Connection string of the database owner | The deploy job, to apply migrations before a release |
| `wallety-webhook-signing-secret` | Random value generated by the setup script | The delivery process signs with it; the built-in receiver in the API verifies with it |
| `wallety-jwt-secret` | Random value generated by the setup script | The API signs and verifies access tokens with it |

## What a deploy does

1. Builds the image and pushes it to Artifact Registry, tagged with the commit.
2. Applies pending migrations as the database owner.
3. Releases a new Cloud Run revision of the API, which runs as the runtime service account.
4. Releases the delivery process: the same image started with `dist/worker.js`, private, with its own identity.
5. Calls `GET /health` on the public URL and fails the job if the API cannot reach the database.

## Webhook delivery

Every posted transfer writes an event to an outbox table in the same transaction. The delivery process sends
each event to the receiver over HTTP, signed with HMAC-SHA256, and retries with exponential backoff.

Cloud Run only gives CPU while a request is in flight, so the delivery process does not poll: `POST
/internal/dispatch` drains the outbox inside the request, retries included. In docker-compose it runs as an
always-on container and polls on a timer instead (`WORKER_POLL_INTERVAL_MS`).
